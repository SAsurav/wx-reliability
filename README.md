# 微信批量触达 · 可靠性工程的实证部分

在一套**不给控制权、状态不可信、结果不可观测**的外部系统上，做可验证的批量操作。

> 结论一句话：这不是「写了个自动发消息的脚本」，而是把系统目标从「让它跑起来」换成
> 「**让它跑错的时候能被发现**」。下面所有数字都能用 `stats.py` 从原始记录复算。

## 可复现的数字

```powershell
python stats.py          # 读数
python stats.py --sample 20   # 导出脱敏样例
```

## 13 人未送达的归因（这是设计结果，不是系统故障）

| 原因 | 人数 | 例子 |
| --- | --- | --- |
| 短名 / 英文名 / 昵称歧义 | **7** | Qing、YANG、H、Sunny、阳光、原 |
| 名称是公司而非个人 | **5** | 多浦乐泵业TOPSFLO、掌阅科技、航天工程装备 |
| 名称与微信显示名不一致 | **1** | 王雪梅 |

**这 13 个人是系统主动放弃的。** 微信搜索是模糊的：搜「H」会命中一堆人，一旦勾错，
消息发出去撤不回。所以规则是「匹配不唯一就拒发，转人工」——宁可少发，不可错发。

## 四个关键决策（每个都放弃了更省事的做法）

| 决策 | 放弃了什么 | 为什么 |
| --- | --- | --- |
| **送达判据**：发送后逐人查数据库聊天记录 | 读 UI 回读、看界面提示 | 已选区回读受可见窗口限制（勾 9 只读到 7）；提示是瞬时的。**UI 回读比不校验更危险——它给你虚假的信心** |
| **断点恢复**：每轮开跑前重算「谁还没收到」 | 记录进度、存进度文件 | 任何保存的状态都会偏离真实状态；重算是幂等的，重跑不会重复发送 |
| **名字匹配**：空白规范化 + 完全相等，不唯一就拒发 | 模糊匹配命中第一个就选 | 一次错发无法撤回。代价是主动放弃一部分人 |
| **输入方式**：ValuePattern 直接给搜索框赋值 | SendKeys 模拟键盘 | 键盘事件发给「当前焦点窗口」——调试时曾把 ESC 打进编辑器，窗口直接消失 |

## 边界（写清楚）

- **代码不公开**：涉及真实业务数据与第三方客户端的自动化，只公开统计方法与脱敏样例。
- `stats.py` 依赖本地原始 CSV，仓库里的 `sample_sent.csv` 是脱敏后的 20 条样例（姓名已替换）。
- 这套方案只适合可控的内部场景短期使用，不适合作为对外服务的基础。

## 这套经验怎么迁移到 Agent

| 这里 | Agent 里 |
| --- | --- |
| 控件对象不可信 | 模型输出不可信 |
| 右键可能落空 | 工具调用可能失败或选错 |
| 数据库快照会过期 | 上下文会被压缩、状态会漂移 |
| 消息发出去撤不回 | 副作用执行后无法回滚 |

四个手段可以直接搬：数据库核验 → 用评测集核验输出而不是相信模型自称做对了；
重算未送达名单 → 每轮从真实状态重建；不唯一就拒发 → 不确定就转人工；
焦点守卫 → 工具调用前校验前置条件。

> Agent 的质量问题，本质上和自动化脚本的可靠性问题是同一个：
> 你不知道它下一步会做什么，所以必须在它能做错的地方，提前放一个可验证的检查点。
